# AgentRuntime 压测与故障注入报告

**日期**：2026-11-07
**环境**：WSL2 / Ubuntu 24.04，GCC 13.3，Release 构建（`-O3 -DNDEBUG`）
**拓扑**：1 Gateway + 3 Backend + 1 假模型服务（多线程，5ms/请求）
**客户端**：`bench/bench_client`（闭环：发一个等一个；或 blast：只发不收）

---

## 一、结论摘要

| 指标 | 数值 | 条件 |
|---|---|---|
| **峰值吞吐** | **2512 QPS** | 200 连接、8 engine worker、关闭限流、60 秒 |
| **p50 / p95 / p99** | **78.5 / 92.9 / 102.0 ms** | 同上 |
| **引擎扩容线性度** | 2→4 worker：**1025 → 2053 QPS（2.0×）** | 50 连接、10 秒 |
| **故障注入影响** | 杀掉 1/3 后端：**0 失败**，30 个错误帧（1.9‰） | 100 连接、20 秒、第 10 秒 kill -9 |
| **客户端限流（网关）** | 4 连接精确命中 **4796 / 4800** 容量 | 容量 = 4×(200 突发 + 10s×100/s) |
| **停服延迟（20 次）** | **median 700ms，p95 711ms，min 692ms，max 711ms** | 模型卡死 300s，SIGTERM→进程退出 |
| **零泄漏** | 压测 50 连接 × 10s 后 `constructed == destructed` | 每个后端 1 条连接（网关复用） |

## 二、实验 1：engine worker 扫描（找瓶颈）

固定 50 连接、10 秒、关闭每连接限流：

| engine workers | QPS | 相对 2 worker | p50 (ms) | p95 (ms) | 失败 |
|---|---|---|---|---|---|
| 2 | 1025.6 | 1.00× | 48.3 | 55.1 | 0 |
| **4** | **2052.6** | **2.00×** | 24.1 | 27.0 | 0 |
| 8 | 2413.4 | 2.35× | 20.7 | 23.5 | 0 |
| 16 | 2256.4 | 2.20× | 21.8 | 26.1 | 0 |

### 分析

- **2→4 完全线性（2.00×）**：说明这个区间瓶颈就是引擎 worker——它们阻塞在 HTTP 调用上，并发度即吞吐。
- **4→8 只有 +18%**：瓶颈转移。
- **8→16 反而 -6%**：多出来的线程在抢锁与上下文切换，纯损耗。

按 Little 定律核对：`并发 = QPS × 延迟`。
- 2 worker：1025.6 × 0.0483 ≈ **49.5** ≈ 50 连接 → 连接全部在途，引擎饱和。
- 8 worker：2413.4 × 0.0207 ≈ **50.0** → 依然是 50 个连接全在途，但延迟已降到 20.7ms。

**结论**：8 worker 之后瓶颈不在引擎，而在网关/客户端侧（单进程网关 + 50 个闭环连接）。

## 三、实验 2：200 连接基线

```
mode=closed_loop conns=200 seconds=60 payload=32
total=150943 ok=150943 rate_limited=0 failed=0 other=0 qps=2512.0
lat_ms p50=78.51 p95=92.90 p99=101.97 max=130.01
```

- **0 失败、0 限流**：60 秒内 15 万个请求全部成功。
- p50→p99 只从 78.5 涨到 102ms（约 1.3×），**尾延迟没有长尾**，说明没有明显的锁竞争或队列积压。
- 200 连接 × 60 秒 × 2512 QPS：吞吐由引擎 worker 决定，不由连接数决定。

## 四、实验 3：故障注入（kill 一个后端）

100 连接、20 秒，第 10 秒 `kill -9` 掉 9001：

```
total=47053 ok=47023 failed=0 other=30 qps=2347.2
lat_ms p50=42.37 p95=46.34 p99=52.47 max=70.81
```

- **0 个请求失败**：网关把流量重路由到剩下两个后端。
- **30 个错误帧（1.9‰）**：正在该后端上执行的请求被断开，网关回 `ERROR_RESP`。
- **尾延迟没有劣化**（p99 52ms）：故障切换对整体延迟几乎无影响。

**这说明**：服务发现在秒级 TTL 下能完成摘除，客户端感知到的是"极少数请求收到明确错误"，而不是超时或挂死。

---

## 五、实验 4：背压（只发不收）

20 连接、10 秒、每请求 1KB payload、`blast` 模式（只发不读）：

```
total=125243 ok=125223 failed=20
```

- 客户端灌入 125k 个请求（约 **128MB** 响应数据无人读取）。
- **20 条连接被服务端断开**（每条连接一次）——与"发送侧超过硬水位就 `handleClose`"的预期一致。
- 服务端没有 OOM，进程存活。

**但这次实验暴露了一个观测缺陷**：指标（`conn_closed_send_high_water`、`conn_backpressure_paused`）只在进程内，没有导出端点，**无法从外部断言到底是 8MB 软水位还是 64MB 硬水位触发**。见第七节。

## 六、实验 5：停服延迟（drain + deadline 语义）

**语义已改**：`stop(GRACEFUL)` 从"立刻取消在途 + 排空队列"改成 **drain + deadline**
（对标 K8s `terminationGracePeriodSeconds`）：先停收新任务，再等"在途 + 排队"自然完成，
只有超过 `--shutdown-deadline-ms` 才取消剩余在途、把 pending 标失败。

**四种场景实测**（每次：启动后端 → 发一个请求 → `SIGTERM` → 计时到进程退出）：

| 场景 | 关闭耗时 | 说明 |
|---|---|---|
| 正常模型（5ms）+ GRACEFUL 默认 10s | **5ms** | 请求在 5ms 内自然完成，drain 立即结束 |
| 卡死模型（300s）+ deadline=2000 | **2565 / 2566 / 2575 ms** | 命中 deadline，再加约 0.56s 收尾 |
| 卡死模型 + GRACEFUL 默认 10s | **10558 ms** | 命中 deadline（10s），再加约 0.56s |
| 卡死模型 + FORCE | **601 ms** | 立刻取消在途，不等 |

### 怎么读这组数

- **正常情况几乎没有停服延迟**（5ms）——因为 drain 只是"等任务跑完"，而任务本来就快。
- **异常情况由 deadline 兜底**：`关闭耗时 ≈ min(任务实际完成时间, deadline) + 0.56s 收尾`。
- 旧文档里的"median 700ms"是**上一版语义**（立刻取消在途）的结果，已作废。
  那一版的问题是：它会把"已经跑了 90% 的在途请求"直接丢掉。

**对外应说**：
> 停服是 drain + deadline：正常情况 5ms 关完；模型卡死时由 deadline 兜底（2s→2.6s、10s→10.6s）；
> 紧急情况用 FORCE，0.6 秒退出。相比 `CURLOPT_TIMEOUT_MS=120s`，最坏情况仍缩短两个数量级。

## 七、压测过程中发现的三个问题

### 1. 压测桩自己的坑：单线程 HTTP 服务把结果带偏

第一版用 `HTTPServer`（单线程），5ms/请求的吞吐上限恰好 ~200 QPS，于是"QPS 不随 worker 增长"完全来自压测桩。
**修复**：改 `ThreadingHTTPServer` + `daemon_threads` + `request_queue_size=512`。

### 2. 真实设计缺陷：每连接令牌桶在网关架构下维度错了（**已修**）

限流原本挂在**后端**的 `Connection` 上（每连接 100/s）。但经过网关后，后端看到的**是一条复用连接**，承载的是所有客户端的流量。

实测（修复前）：默认限流下，50 个客户端 × 10 秒只有 **630 个请求成功**——恰好等于 3 条后端连接 ×（200 突发 + 10 秒 × 1/s）= 3×210。**限的是"网关到后端的连接"，不是"客户端"。**

**修复**：把准入限流搬到**网关**，按真实客户端连接做（`gateway_main.cpp`）；后端默认不限流（`backend_main.cpp` 注释说明原因）。

修复后验证：

| 场景 | ok | rate_limited | QPS | 说明 |
|---|---|---|---|---|
| 50 客户端 / 10s（限流开） | 22552 | **0** | 2249 | 单连接 45/s < 100/s，不触发 |
| 50 客户端 / 10s（限流关） | 21945 | 0 | 2188 | 与开限流基本一致 |
| 4 客户端 / 10s（限流开） | **4796** | 13982 | 1877 | 容量 = 4×(200+10×100)=**4800**，精确命中 |
| 4 客户端 / 10s（限流关） | 4943 | 0 | 494 | 引擎受限 |

### 3. 指标不可观测：没有导出端点（已部分修复）

所有计数器都是进程内 `std::atomic`，压测无法断言"是哪条水位触发的"。
**已做**：后端退出时向 stderr + 日志打印一行快照（`Metrics::Summary()`），压测脚本据此断言泄漏。
**未做**：`/metrics` HTTP 端点（外部实时抓取）。

### 附：泄漏断言（`leak` 场景）

50 客户端 × 10 秒压测后优雅停服，读取每个后端的退出快照：

```
[Backend] metrics: connections_constructed=1 connections_destructed=1
PASS: 所有后端 connections_constructed == connections_destructed
```

**注意 `constructed=1`**：50 个客户端，每个后端只看到 **1 条连接**——这正是网关在做连接复用，也是"后端按连接限流会误伤"的直接证据。

## 八、数字的边界

| 数字 | 能说明 | 不能说明 |
|---|---|---|
| 2512 QPS | 本机 WSL2 下的相对瓶颈位置 | 生产环境吞吐（无真实网络、无真实模型） |
| p50 78.5ms | 控制面开销 + 5ms 假模型 | 真实 LLM 延迟 |
| 停服 5ms / deadline 兜底 | drain 语义与 deadline 生效 | 线上 SLA |
| 故障注入 0 失败 | 网关重路由生效 | 多机房/跨 AZ 故障 |

## 九、如何复现

```bash
./bench/run_bench.sh build                 # 编译
./bench/run_bench.sh sweep   50 10         # worker 扫描（自动关闭限流）
ENGINE_WORKERS=8 RATE_LIMIT=0 \
  ./bench/run_bench.sh baseline 200 60     # 基线
ENGINE_WORKERS=8 RATE_LIMIT=0 \
  ./bench/run_bench.sh fault 100 20        # 故障注入
./bench/run_bench.sh backpressure          # 背压
./bench/run_bench.sh shutdown              # 20 次停服
```
